# Security

Hearth holds health information about older people, so it is built to protect it by default.
This page explains what it protects against and how to report a problem.

## Reporting a problem

Please do not open a public issue for a security problem. Use GitHub's private
**Report a vulnerability** form on this repository (Security tab), and include the steps to
reproduce it. You will get a reply as soon as possible.

## What Hearth protects against

| Threat | Protection |
|---|---|
| Guessing passcodes | Passcodes must be at least 8 characters and are checked against common passcodes, simple patterns (`11111111`, `abcdefgh`, `121212…`) and the person's own name. Sign-in locks for 15 minutes after 5 wrong tries from one place (25 for a circle, 20 for an address). |
| A guessing attempt going unnoticed | Every wrong passcode for a circle appears in its History, and the elder gets an email (at most hourly) when sign-in is paused. |
| A stolen database | Passcodes are stored only as salted scrypt hashes. |
| Finding out which circles exist | Every failed sign-in gets the same message and takes the same time, whether or not the circle code exists. |
| A stolen or forgotten session | Sessions end after 12 hours unused and 3 days in total, whatever the cookie says. Removing someone, giving them a new passcode, or pressing **Sign me out on all devices** ends their sessions at once. |
| Session cookie theft or tampering | Cookies are signed, `HttpOnly` and `SameSite=Lax`. Over HTTPS they are also `Secure` and use the `__Host-` prefix, so no other site or subdomain can set them. A new session is started at sign-in (no session fixation). |
| One circle reading another's data | Every database query is scoped to the signed-in circle; IDs from another circle return 404. |
| Doing more than a role allows | One role-to-permission table, checked by every page and action. Only the elder manages the circle, and nobody can remove the elder. |
| Cross-site request forgery | A per-session token on every form, compared in constant time. |
| Cross-site scripting | Templates escape all output, and a strict Content-Security-Policy allows only the app's own scripts and styles (no inline scripts). |
| Clickjacking and cross-origin attacks | `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy: same-origin`. |
| Downgrade to plain HTTP | Over HTTPS: `Strict-Transport-Security` for a year and `upgrade-insecure-requests`. |
| Health data left in caches | `Cache-Control: no-store` on every page. |
| Oversized or malformed input | 64 KB request limit, and every field validated and length-capped on the server. |
| Open redirects | Redirect targets are limited to paths on the same site. |
| The scheduler endpoint | Hidden unless a token is configured, then needs that bearer token (constant-time comparison). |
| AI misuse | Gemini receives only the sentence typed, with the key in a header. Its answer is schema-validated, only pre-fills a form a person must check, and calls are rate-limited. |
| Vulnerable dependencies | Minimum versions include known fixes, `pip-audit` runs in CI, and Dependabot proposes updates weekly. Ruff's security rules (Bandit) run on every push. |
| Secrets in the code | None: everything sensitive comes from environment variables; `.env` is git-ignored, and on Render the secret key is generated by Render. |

## Not covered (yet)

- **Encryption at rest:** the SQLite file is not encrypted. Use an encrypted disk, or move to a
  managed database with encryption, before storing real patients' data.
- **Two-factor sign-in:** passcodes are the only factor, as the challenge specified.
- **Real email in the demo:** the public demo records emails on its Emails sent page instead of sending them.
